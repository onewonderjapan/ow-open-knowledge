### 4.3 社交类：唯一外发 Bot；仅脱敏知识；外部习得与既有 KB 隔离

**规则**：只有社交 Bot 对外部社区说话；只外发脱敏知识；外部交换学到的东西**单独存放**，不得写入既有知识库。

**操作化**：

1. **发言权**：仅 **neng社交的** 可对外发帖/回复。其他 Bot 最多把「建议外发草稿」放入 `{ISOLATION_ROOT}/outbound-queue/`。
2. **外发内容**：须完成 §4.6 脱敏且抽查通过。客户实名 / 个资 / 密钥 / 未发表 IP 等按 L3 处理；对照 `agent-cultivation/data-classification.md`。未拍板 #7 前：队列稿停在「待脱敏」，**11:00/16:00 只允许发已抽查通过的稿；否则空窗**。
3. **隔离区（逻辑路径，物理仓拍板 #3）**：
   - `{ISOLATION_ROOT}/external-exchange/raw/YYYY-MM-DD-<slug>.md` — 外部原文摘要（仍脱敏，默认 L2 起）
   - `{ISOLATION_ROOT}/external-exchange/learned/YYYY-MM-DD-<slug>.md` — 习得条目（默认「待验证」）
   - **禁止**写入：`ow-open-knowledge` 主题目录、W2 知识库正本、`ai-knowledge-local` 活跃已验证集、CDN `kb-data.json` 生产线。
4. **与 daily-intel 关系**：面向制作群的「今日份」可继续用 `owd-daily-intel`；其中标「社区帖 / 非永久」的条目**不等于**已入库，也不等于隔离区正本。
5. **live 发布**：非模拟队列的对外 live 属确认门（附录 B / 拍板 #8），未批准不得发。

**节奏**：工作日 11:00 必跑（可空窗）；16:00 第二窗有就绪队列才发；20:00 习得写入隔离区。隔离区写入成功 ≠ 可入库。

### 4.4 分析类：未验证/外部知识经高强度分析；拆成「可入库」与「待验证」

**规则**：未验证或外部知识，使用 grok-4.6、effort **xhigh** 做分析；结果拆成 **可入库** vs **待验证**。

**操作化**：

1. **触发**：社交隔离区新条目、外部公开信息、未经内部复现的技巧/结论、调查记录中的「假设」、整理稿中标「待验证」的段落。
2. **发起约定（运行默认，不替代拍板 #12）**：秘书在 16:30 列出当日队列（隔离区新文件 + INV 假设 + staging 待验证）；源 Bot 在 16:30 前把输入 path 补齐。由秘书或源 Bot 按 grok-4.6 / xhigh 写出 AN。名单中**不另设**「分析 Bot」。周五 15:00 爆款周复盘若已覆盖当日队列，分析窗写空窗「并入 AN-…」。
3. **分析输出格式**（逻辑路径：`{OPS_ROOT}/staging/AN-YYYYMMDD-<序号>.md` 或与 INV 同目录，二选一写在 AN 头字段，禁止两份正本）：

```markdown
# 分析 · YYYY-MM-DD · <标题>

- 分析 ID：AN-YYYYMMDD-<序号>
- 模型约定：grok-4.6 / effort xhigh
- 输入来源：<隔离区逻辑 path / INV-…>
- 机密分级：…
- 发起 Bot：

## 可入库（Promotable）
| 条目 | 依据 | 建议目标 path | 仍需的人工确认 |
|---|---|---|---|

## 待验证（Pending）
| 条目 | 缺什么证据 | 建议复现实验 | Owner |
|---|---|---|---|

## 明确丢弃 / 不入库
- …（写理由；丢弃 ≠ 删除原文件）
```

4. **门禁**：标「可入库」仍须 **§4.7 晋升门**（脱敏复查 + 指定审批，拍板 #4）后才能进入公开/正本 KB。AN 本身不是入库许可。
5. **节奏**：工作日 16:30–17:30 批处理当日队列；重大外部争议可即时加塞（加塞须在日向「加塞」栏留痕，避免无主）。

### 4.5 管理类：定期审计仓库与路径；杜绝孤儿文件

**规则**：定期审计各仓库与路径，不留无人认领的孤儿文件。

**操作化（管仓库的主责，秘书抽查）**：

1. **日检（10:00）**：对照 `ai-ops/repos.md`——有无远端、未推送提交、救援分支是否超期。产出可并入当日健康检查短记录（或空窗「无异常」）。
2. **周检（周日 11:00）**：
   - 无 README / 无 Owner 标注的新建路径；
   - `{OPS_ROOT}` 下 `investigations/` `projects/` `staging/` `promotions/` 与 `{ISOLATION_ROOT}` 下 `external-exchange/` `outbound-queue/`、以及 `audits/` 自身，超过阈值仍未关闭的条目（阈值见下，**不写死 N=14**）；
   - 公开仓是否混入 L3；
   - `owd-knowledge-hub` 是否被误当作内容仓写入；
   - 逻辑路径是否被当成未定物理仓强行 push。
3. **超期阈值（拍板 #5 未决前的对照算法，不是已决政策）**：报告里对每条暂存同时标注是否超过 14 天、30 天、以及按 L 级（L1=30 / L2=14 / L3=7）。**不自动归档、不删除**。删除必须机主确认（对齐 AI_RULES / 附录 B）。
4. **审计报告格式**：`{OPS_ROOT}/audits/YYYY-MM-DD-repo-orphan.md`，含：孤儿清单、建议归档/认领/删除、三套阈值对照。物理仓见拍板 #2（选项含 `ai-ops/audits/`，正文不预先锁死）。
5. **节奏**：工作日 10:00 + 周日 11:00。秘书抽查在周日 **12:00**，以审计文件存在为前提。

### 4.6 脱敏执行步骤（步骤可跑，执行者见拍板 #7）

规则要求「只外发脱敏知识」；本小节补**怎么做**。谁来做 → 拍板 #7。未拍板前执行运行默认：停在待脱敏。

**何时必须脱敏**：对外队列、拟公开晋升、写入 daily-intel 的句子、隔离区 raw/learned（raw 也须去密钥/个资，不得存可复制秘密）。

**步骤**：

1. **打标**：源 Bot 在文件头写 `摄入状态：待脱敏` + 机密分级。缺分级 = 按 L3 处理（只加严，不改分级政策正本）。
2. **执行者**（#7 选定前不得 live、不得晋升）：按附录 D 清单处理，产出**三件套**（拍板 #7B 亦提到三件套；此处把文件名写清，不把 #7B 当作已选）：
   - `RED-YYYYMMDD-<序号>-src.md`：分级原文（不外发、不进公开仓）
   - `RED-YYYYMMDD-<序号>-out.md`：脱敏稿
   - `RED-YYYYMMDD-<序号>-map.md`：对照表（字段 → 替换策略；**禁止**把可逆明文密钥写回表内）
3. **抽查**：执行者不是秘书时，由秘书抽查；执行者已是秘书时，由管项目的抽查。抽查对照附录 D，抽查记录写在 `-out.md` 头字段 `抽查：通过/退回`。
4. **通过**：外发稿可进 outbound-queue 标「就绪」；公开候选可进晋升申请。
5. **退回**：状态回到待脱敏；写 ALT 告警（类型=`脱敏退回`）；不得改用原文外发。
6. **管线**：若将来选定 #7B（ai-stack 或其继任），仍须产出上述三件套并完成抽查。本调研**未核实**该管线已可调用，不得把「跑了某脚本」写成已脱敏。

### 4.7 晋升门执行步骤（步骤可跑，审批人见拍板 #4）

「可入库」是分析结论，不是入库许可。晋升门把「可入库」变成「已摄入」。

**申请文件**：`{OPS_ROOT}/promotions/PRM-YYYYMMDD-<序号>.md`（格式见附录 E）。

**硬条件（缺一不可；未拍板 #4 前即使全满足也不得 merge）**：

1. 有 AN- ID，且该条目列在「可入库」表。
2. L1 拟公开 / 拟外发：脱敏三件套存在且抽查通过。L3：**禁止**公开晋升。L2：只允许社内正本，仍须审批，不得进 open-knowledge 公开面。
3. 目标 path 落在已核实允许清单（open-knowledge 主题目录，或拍板后写明的正本目录）。禁止目标为 `owd-knowledge-hub` 内容文件、禁止直写 CDN `kb-data.json`。
4. `ai-knowledge-local` 投影不得早于正本；正本未写则禁止投影。
5. 审批人按拍板 #4。未选定审批人 = 未批准。
6. 涉及确认门（附录 B：对外 live、删文件、客户 L3 原文、改五规则等）→ 先走拍板 #8，不走「低风险 L1 代行」绕过。

**通过后**：只写申请中的目标 path；把 staging 头改为 `已摄入` 并留下 PRM- ID；**不删除** staging 原文（删文件走确认门）。  
**拒绝后**：条目回「待验证」或「明确丢弃」，写原因；不删原 INV/AN/隔离文件。

### 4.8 排程值守与失败告警（步骤可跑，Owner 见拍板 #9，通道见拍板 #13）

排程是意图，不是已上线的 cron。本节定义**如何发现没交卷、如何告警**，不把 Owner 写成已决。

**登记**：`{OPS_ROOT}/schedules/bot-cron-intent.md` 每行至少：

| Bot | 任务名 | 意图时刻 | 星期 | 产出文件名模式 | 成功判据 | 宽限 | 空窗是否允许 |
|---|---|---|---|---|---|---|---|

内容与 §3 表保持一致。修改意图时刻 = 改本计划运营段落，须在日向留痕；若改的是政策（谁必须跑、是否对外 live）→ 拍板。

**值守步骤（#9 未决前的运行默认）**：

1. 产出 Bot 在意图时刻 + 30 分钟内自检：有产出或空窗记录。
2. 秘书 09:00 日向**必扫**昨日全部意图行：交卷 / 空窗 / 失败。缺扫本身算秘书该窗失败。
3. 管项目的周三 15:00 把「连续失败」升级为阻塞（见下）。
4. 不假设 IM 已接通。告警**第一落点**永远是 `{OPS_ROOT}/alerts/ALT-YYYYMMDD-<序号>.md`。外部通道选定前（拍板 #13），禁止声称「已 @ 某人」。

**失败定义**（命中任一）：

- 宽限过后既无产出也无空窗记录；
- 产出缺 §4 对应必填字段；
- 写到禁止路径（公开主题目录未晋升、knowledge-hub 内容、CDN、W2 正本、把逻辑路径当未定仓 push）；
- 对外 live 未经确认门；
- 脱敏退回后仍进入就绪队列。

**告警文件必填**：`ALT-ID / 时间 / Bot / 任务 / 失败类型 / 已影响路径 / 建议动作 / 是否触及确认门`。

**升级时钟**（从宽限结束起算，工作日）：

| 时刻 | 动作 |
|---|---|
| T+0 | 发现者写 ALT；状态=`open` |
| 下一工作日 09:00 | 必须出现在秘书日向「失败」栏；未出现则再写一条 ALT（类型=`日向未扫失败`） |
| 连续 2 个工作日同一任务失败 | 管项目的列为阻塞，周三 15:00 升级给秘书（若当天不是周三，日向即升级，不等周三） |
| 触及对外 live / L3 / 删文件 / 公开仓误写 | **立即停该窗口**，请示机主（确认门）；不自动重试外发 |
| 已补交且格式通过 | ALT 改为 `closed`，写补交 path；不删除 ALT 文件 |

**禁止**：失败后自动补发对外内容；用「下次再跑」吞掉 ALT。对内摘要允许下一窗口补跑，须在 ALT 写补跑时刻。
