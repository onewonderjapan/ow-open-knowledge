# 踩坑清单（実装knowhow — これ自体が商品）

> 参考実装を作る過程で実際に踏んだ坑を全て記録する。顧客案件の見積り精度と信頼の源泉。

## 2026-07-03 薄切片構築時

1. **マスキングの再帰マッチ**: 「佐藤健一様→担当者甲様」置換後、人名パターンが「担当者甲様」を
   再度人名と誤認して二重置換。→ 置換済みラベルをスキップする防護を必ず入れる。
   教訓: 脱敏は「置換順序と再入」のバグが出やすい。テストケース必須。
2. **構造検査の見出し誤検知**: 文書タイトル(h1)直後に章見出しが来る正常パターンを「空の章」と
   誤報。→ h2以下のみを対象に。
3. **Windows コンソールの文字化け**: UTF-8出力が cp932 コンソールで化ける(動作には無害)。
   デモ時は必ずファイル出力側を見せる or `chcp 65001`。
4. **CJKユーザー名問題(画像生産PJ側から継承した知見)**: HuggingFace/sentencepiece系は
   `C:\Users\<user>\` 配下のキャッシュを読めない → `HF_HOME=C:\hf_cache`。
   .ps1 に日本語を書くなら UTF-8 BOM 必須。
5. **APIキーが無い段階のデモ**: Claude Code の `-p` モード(サブスク認証)で本物のLLM出力を
   デモできる。ただし PoC 限定・本番は API 契約(規約と商用条件の確認を先に)。

## 2026-07-03 実データ(PPTX提案資料)投入時

6. **PPTXの本文はshape単位で散らばる**: テキストフレーム/表/グループ/ノートを全部歩く必要がある。
   → tools/pptx_extract.py。スライド順は保たれるがレイアウト上の読み順とは限らない点に注意。
7. **実文書の人名は敬称なしが普通**(体制図の自社側)。「X様」パターンだけでは半分漏れる。
   → 実名辞書(entities.local.json, gitignore)方式が本命。NER(GiNZA)導入までは辞書整備が必須工程。
8. **人名ラベルの容量**: 甲乙丙丁…の8個では実文書(36名)で即座に衝突。連番(担当者01..)に変更。
9. **同一実体の表記ゆれ**(「株式会社◯◯」「◯◯製作所」「◯◯」の混在、姓のみ表記): custom直接指定で
   同一ラベルに寄せる。会社名を自動連番にすると表記ゆれで別会社に見えてしまう。
10. **拠点名・製品名も機密**(データセンタ所在地、サービス名)。人/会社の2種別では足りない
    → custom {実語:伏せ字} を追加。
11. **姓名間の空白が全角/半角混在**している実文書がある。辞書には「見たままの表記」を登録し、
    リークチェック(断片検索)で漏れを検出して辞書に追補するループが実用的。

## 2026-09-12 公開版の脱敏層レビュー時

12. **正規化(NFKC)を挟まないと全角がそのまま漏れる**: `０３−１２３４−５６７８` は半角前提の
    電話正規表現をすり抜けて素通りしていた。日本語文書では全角数字・全角＠が普通に来る。
    → `mask()` の入口で NFKC を通す。副作用として `（新規）`→`(新規)` のように全角括弧も
    半角化されるが、漏れを防ぐ方を採る（意識的なトレードオフ）。
13. **ダッシュ類の全文置換は日本語を壊す**: 電話の区切り揺れを潰すため `ー`(U+30FC) を `-` に
    全文置換したら「承認フロー」が「承認フロ-」になった。U+30FC は区切り記号と長音符の兼用。
    → 全文置換ではなく、**数字に挟まれた区切り位置に限って**正規表現内で許容する。
    教訓: 正規化は「どの範囲に効かせるか」まで設計しないと別の事故になる。回帰テストで発覚。
14. **区切りなしの電話番号を忘れる**: `0312345678` / `03 1234 5678` / `03(1234)5678` は実文書に
    普通にある。区切りが `-` だけという前提は成立しない。→ 3形態を明示的に列挙し、
    前後の数字を `(?<!\d)(?!\d)` で除外して日付・席数の誤検出を避ける。
15. **会社ラベルもラベル枯れする**(項8の教訓が会社側に適用されていなかった): `A社`〜`N社` の14個
    固定で、15社目以降が `min()` で静かに `N社` に潰れ、監査表の1:1対応が壊れていた。
    → `A社`..`Z社`,`AA社`.. とアルゴリズム生成で上限を撤廃。
    教訓: **静かな飽和は例外より危険**。上限がある実装は必ず枯れるケースをテストする。
16. **役職名を人名と誤判定する**: 「人事部長」が `担当者01部長` になり、しかも監査表に
    実在しない人物 `{"人事": "担当者01"}` が入っていた。文意も監査記録も同時に壊れる。
    → 役職(部長/課長/社長)の前は組織語(人事/営業/総務…)を除外リストで弾く。敬称(様/氏/さん)側は
    従来どおり緩く伏せる(辞書外の人名を拾うため)。
17. **逐次 `str.replace()` は短い実体が長い実体を食い潰す**: custom の「田中」が先に置換され、
    辞書の「田中商事」が二度と一致しなくなる。→ 辞書+customを**1本の正規表現に畳んで最長一致優先の
    単一パス**にする。順序依存のバグは順序をなくして消す。
18. **法人格が伏せ字と二重に残る**: 「株式会社田中商事」→「株式会社A社」という壊れた出力。
    → 法人格を実体と一体で消化する。
19. **RAGで召回した先例文書は脱敏対象から漏れやすい**: 要件書だけ脱敏して、プロンプトに差し込む
    過去設計書は生テキストのままだった。デモ語料は匿名済みなので気付けない。
    → 出境するテキストは**プロンプト組立の直前で全て**脱敏する。
    教訓: 「何が外に出るか」はデータの入口ではなく**出口で**数える。
20. **SKILL.md に YAML frontmatter が無いとローダが無視する**: `cloud-patterns/` は
    「Claude Code 系ツールにそのまま置ける」と README で謳っていたが、4本とも
    `name` / `description` の frontmatter が無く、`scan_skills.py` は警告付きで
    スキップしていた（6 skills / 4 warnings）。本文がいくら良くても skill として
    認識されない。→ 公開する SKILL.md は必ず frontmatter を付け、
    `scripts/check_skills.py` で門番する。ディレクトリ名と `name` も揃える。
