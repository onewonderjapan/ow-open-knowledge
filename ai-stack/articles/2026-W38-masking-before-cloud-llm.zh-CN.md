# 上云前先脱敏：企业 AI 薄切片里，客户明文为什么不该直接进云端 LLM

## 问题场景

售前或交付同事手里有一份「刚到的需求」：里面常夹着公司名、人名、电话、邮箱、金额。若把原文直接贴进云端 LLM，等于把 L3 标识一次性送出门外。事故往往不是模型「记错了」，而是**送信前没有一道可审计的边界**——事后翻聊天记录，也很难证明「当时送出去的到底是不是原文」。

仓库里的 `ai-stack` 把这条边界做成薄切片：需求文档 → **脱敏** → 社内先例检索（RAG）→ 云端或 stub 起草 → 本地结构检查。演示时，对外能亮出的关键产物是「实际离楼的那份 masked 稿」和审计用的 report，而不是原始附件。对内 dogfood 与对外 PoC 共用同一套接口，差别只在 provider 与数据是否虚构。

## 为什么先脱敏

`agent-cultivation/data-classification.md` 把数据分成三段：L1 可公开、L2 社内、L3 机密。客户实名、个资、客户文书原文、密钥等属于 L3——**禁止原文投入任何云端 AI**；需要模型时，必须先脱敏（伏字化），或全程本地处理。

先脱敏的理由很朴素：

1. **合规默认**：判断不清时按更高一级处理；宁可多遮，不可漏传。
2. **可还原、可审计**：同一实体在全文映射到同一伏字，逆映射表留本地，云端会话里不应出现真名对照。
3. **接口可替换**：薄切片用正则 + 字典；生产可叠 NER，但「先遮再送」这条契约不变。

## 薄切片怎么跑（stub 可离线）

按 `ai-stack/README.md`，stub provider **不需要网络与 API key**：

```bash
python -m venv .venv
source .venv/bin/activate   # Windows 用 .venv\Scripts\
pip install -r requirements.txt
python pipeline/run.py demo_data/incoming/new_rfp.md --provider stub
```

关注输出：`out/<name>_masked.md`（实际离楼内容）、`out/<name>_draft.md`（草稿）、`out/<name>_report.json`（审计轨迹）。`demo_data/` 内全部为虚构公司与人名，可安全演示。

脱敏机制（高层，见 `masking/masker.py`）：先做 NFKC 归一，减少全半角写法造成的漏检；再合并可提交的 `entities.json`（仓内虚构样例）与 gitignore 的 `entities.local.json`（实名只留本地）。按层处理——字典 / custom 已知实体、法人格与「様 / 氏 / さん」等敬称类模式、电话 / 邮件 / 邮编 / 金额 / URL 等正则。同一实体全文同一伏字（如「A 社」「担当者01」），避免前后文各叫一名导致模型对不上。设计取舍是**过量遮盖可接受，漏检不可接受**。薄切片限制：字典外人名多依赖敬称线索；更强 NER（如 GiNZA）是升级方向，不是本稿范围。双向检查的思路是：送信前遮一次，产出回来再对照泄漏模式抽查——evalkit 与生成侧共用规则，避免「检查比生成更松」。

## 对外可讲技术点

- **边界在送信前**：云端只收已脱敏文本；映射与实名对照不离本地，会话记录里也不该出现「真名 ↔ 伏字」对照表。
- **一层可演示的管线**：mask → RAG → draft → check；provider 可换 stub / CLI / API，层与层之间接口固定，可独立加厚。
- **安全控件当回归测**：改 masking 规则要配测试（README / CLAUDE 约定），避免「演示能过、规则一改就漏」。
- **分级口语化**：L3 不直送云；先伏字或本地处理——这句话本身就是 L1 可公开话术，不必泄露任何客户细节。
